# Прошивка ведущего контроллера ESP32

**Отдельный проект ESP-IDF**.

Для отладочной платы классической ESP32:

1. Установить ESP-IDF 5.x, открыть терминал с активированным окружением ESP-IDF.
2. Сверить пины UART2/RS485 в `main/main.c` со схемой платы, адреса головок — с `Inc/modbus_board.h` проекта STM32.
3. Подключить плату к компьютеру USB-кабелем **с передачей данных**, затем выполнить:

   ```sh
   cd esp32_master
   idf.py set-target esp32
   idf.py build
   idf.py -p <ПОРТ_ПЛАТЫ> flash monitor
   ```

При конфликтах кодировок в idf powershell выполнить:  

```sh
[Environment]::SetEnvironmentVariable("PYTHONUTF8", "1", "User")
 $env:PYTHONUTF8 = "1"  

```
Проверка:  

```sh
python -c "import sys, locale; print(sys.executable); print('utf8_mode=', sys.flags.utf8_mode); print('file_encoding=', locale.getpreferredencoding(False))"
C:\Espressif\python_env\idf5.3_py3.11_env\Scripts\python.exe
utf8_mode= 1
file_encoding= utf-8
```

Если так, значит все хорошо

---

Угол передаётся как `uint32` в **микроградусах**, старшее 16-битное слово первым, и выводится с шестью знаками после запятой. Сборка использует `main/main.c` и переносимый автомат `main/workflow.c`.

Полная инструкция по установке, загрузке, подключению и таблице регистров: [документация Modbus](../docs/modbus_rtu.md#2-как-прошить-esp32-esp-idf-usb-а-не-iar).

## Команды в `idf.py monitor`

После загрузки программа **ждет команду** в приглашении `encoder>`. Список доступных команд:

```text
help
scan
poll 1,2,7
stop
calib 7,1
next
```

- `scan`-- полный поиск ID 1..247, без записи регистров.
  Выводит и сохраняет найденные адреса, затем возвращается в ожидание команды.
- `poll [id,id,...]` — рабочий опрос выбранных ID по циклу SNAP -> STATUS -> READ
- `calib [id,id,...]` —  подготовка последовательной калибровки выбранных ID, первая запись требует `next`.
- Для `poll`/`calib` явный список сохраняет порядок и работает **без предварительного
  scan**. Без списка используется кэш завершённого ручного поиска, по возрастанию ID.
  Если кэш пуст, режим не запускается: указать ID или сначала выполнить `scan`.
- `next` — подтвердить **показанный в журнале** этап: сначала подготовить вращение.
  Требуется перед первым этапом, каждым следующим этапом (включая смену направления)
  и перед первой командой **следующей головке**. Автоматического перехода к ней нет.
- `stop` — отменить процесс. Если калибровка уже
  запущена, передаётся адресная `0x10` и проверяется LIVE-состояние `0x00`.
  До первой команды головке `stop` просто отменяет выбранный режим, без записи.

Если адреса известны, достаточно `poll 1,7` или `calib 7,1` сразу после загрузки.
Для выбора после просмотра поиска: `scan`, дождаться списка, затем `poll 1,7`
или просто `poll` для всех найденных.

Полный поиск занимает примерно **две минуты** при 400 мс на отсутствующий slave.
Проверяется FC04 регистров 0..1, без SNAP: `ready=0` не мешает обнаружению.
Это проверка ответа с совместимым диапазоном регистров.

## Структура кода мастера

Мастер разделен на автомат и аппаратную часть:

```text
UART0-консоль → console_command() → очередь command_t
                                       ↓
                              worker (encoder_bus)
                                       ↓
                  workflow_command() + workflow_tick()
                                       ↓
                              workflow_io_t callbacks
                      request / poll / log / now_ms
                                       ↓
                  request() → mbc_master_send_request()
                                       ↓
                      esp-modbus → UART2 → RS485 → STM32
```

- **`main/main.c`** — интеграция с ESP-IDF. `app_main()` настраивает Modbus RTU
  (115200, 8E1), UART2/RS485, создает очередь, автомат, задачу `worker` и консоль.
  `console_command()` разбирает команду/CSV и копирует `command_t` в очередь.
  Только `worker` вызывает автомат и прикладные Modbus-запросы;
- **`main/workflow.c`** — последовательность действий и проверок: выбор ID,
  ручной поиск, включение poll, шесть этапов calib, подтверждения, ошибки и тайм-ауты.
  `workflow_command()` обрабатывает одну команду, `workflow_tick()` продвигает
  текущий режим.
- **`workflow_t`** (объявлена в `main/workflow.h`) — структура состояния одного
  автомата.
  `state` — текущий режим (`WF_IDLE`, `WF_SCAN`, `WF_POLL`, `WF_CONFIRM`, `WF_CALIB`);
  `found`/`found_count` — кэш ручного поиска, `ids`/`count` — выбранные для режима ID;
  `head`/`step` — индексы головки и этапа; `scan_id` — следующий адрес поиска;
  `seq` — номер снимка; `started`, `failures`, `last_state` — время этапа,
  счётчик ошибок и последнее состояние для журнала. Поле `io` содержит callbacks.
- **`workflow_io_t`** — структура с четырьмя указателями на функции

  | Поле | Реальная функция в `main.c` | Назначение |
  |---|---|---|
  | `request` | `workflow_request` | Синхронный FC04/FC06, результат `bool` |
  | `poll` | `poll_heads` | Полный цикл SNAP → STATUS → READ |
  | `log` | `workflow_log` | Готовая строка в `ESP_LOGI` |
  | `now_ms` | `now_ms` | Монотонные миллисекунды из `esp_timer_get_time()` |

  Эти зависимости передаются при `workflow_init()`. Поэтому `workflow.c` не
  зависит от ESP-IDF: host-тест подставляет вместо UART/часов/журнала свои функции,
  но исполняет настоящий автомат. Набор callbacks хранится внутри `workflow.io`.

### Связь с Modbus

Автомат определяет **что и когда** сделать, библиотека `esp-modbus` — **как передать**
запрос: RTU-кадр, CRC, обмен по UART и тайм-ауты. `workflow_request()` вызывает
обёртку `request()`, которая заполняет `mb_param_request_t` и передаёт его в
`mbc_master_send_request(master, ...)`. `master` — отдельный handle контроллера
esp-modbus; это не `workflow`. После запроса обёртка выдерживает ещё 20 мс.

- **scan:** FC04, input-регистры 0..1 каждого ID 1..247.
- **poll:** `workflow_tick()` вызывает `io.poll(ids, count, seq++)`.
  `poll_heads()` через `request()` отправляет broadcast FC06 в holding[0] (SNAP),
  затем адресные FC04 STATUS (0..1) всех выбранных ID. Только после всех ACK
  выполняются рабочие FC04 READ (0..10). ACK — совпадение `seq` и `ready=1`. SNAP получают и невыбранные головки.
- **calib:** после `next` автомат через `io.request` проверяет LIVE input-регистры
  `0x100..0x102` (состояние, EEPROM_READY, версия `0xCA01`), затем адресной FC06
  пишет команду в holding[1]. Следующие tick читают LIVE до ожидаемого завершения
  и готовности EEPROM; перед следующим этапом требуется новое `next`.
  Адреса и версия заданы в общем для мастера и slave `Inc/encoder_protocol.h`.

`workflow_t` и `workflow_io_t` **не передаются по Modbus** — это локальные структуры
RAM ESP32. На линию уходят только адрес slave, код функции, адрес/количество
регистров и данные в формате Modbus RTU. FC04 input и FC06 holding — разные
адресные пространства; все адреса здесь нулевые, как на проводе.

Вызовы синхронные: tick не является полностью неблокирующим. `worker` ждёт команду
до 100 мс между шагами, а запрос может ждать ответа дольше. Поэтому `stop` не
прерывает уже начатую транзакцию или полный цикл poll.

## Калибровка

| Этап | FC06, holding[1] | Состояние «идёт» → «готово» | Вращение |
|---|---|---|---|
| 1. `buf_k` | `0x14` | `0x70` → `0x80` | Равномерно, любое направление, 10–40 об/мин |
| 2. `offset` | `0x13` | `0x50` → `0x60` | То же |
| 3. `ang_tab`, проход 1 | `0x11` | `0x10` → `0x20` | Угол возрастает, 5–20 об/мин |
| 4. `ang_tab`, проход 2 | `0x12` | `0x30` → `0x40` | **Обратное направление**, 5–20 об/мин |
| 5. Повтор `buf_k` | `0x14` | `0x70` → `0x80` | Равномерно, любое направление, 10–40 об/мин |
| 6. Повтор `offset` | `0x13` | `0x50` → `0x60` | То же |

Реализован указанный двухкратный проход `buf_k/offset` вокруг `ang_tab`;
его достаточность и улучшение точности необходимо проверить на стенде.

Управления двигателем в этом проекте **нет**: направления и скорость задаёт оператор.

Положительный ответ FC06 — только приём команды, **не** завершение калибровки.
ESP32 читает FC04 LIVE `0x100..0x102`, проверяет ожидаемый код и `EEPROM_READY=1`.
Завершение, произошедшее до первого чтения промежуточного состояния, допустимо.
После шестого этапа ESP32 посылает `0x10`, проверяет `0x00`, сообщает COMPLETE
и ждёт `next` для следующей головки. Между проходами `0x11` и `0x12` STOP не посылается.

### Защита и ограничения

- Перед началом **сохранить калибровочные таблицы EEPROM через IAR/SWD**.
  Автоматического резервного копирования, отката и чтения таблиц через Modbus нет.
- Начать список можно только с LIVE-состояния `0x00` и законченной записи EEPROM.
  Уже занятую/оставшуюся в другом состоянии головку программа не перезапускает.
- Тайм-аут **10 минут на этап**, включая запись EEPROM; ожидание оператора вне
  этого тайм-аута. Пять последовательных ошибок LIVE-чтения, неверное состояние
  или ошибка FC06 отменяют **весь список**, не переходя к следующей головке.
- После ошибки ESP32 делает попытку адресного STOP и читает состояние.
  При потере ответа FC06 стартовая команда **не повторяется**: она могла исполниться.
  `STOP ... NOT CONFIRMED` означает, что остановка **не доказана**; проверить
  головку локально, при необходимости восстановить через SWD/перезагрузку.
- STOP выключает все три автомата, возвращает АРУ подсветки, но **не откатывает**
  уже изменённые коэффициенты в RAM/EEPROM и не отменяет начатую I2C-передачу.
  После прерывания до повторного запуска проверить/восстановить калибровки.
- Отключение USB, выход из `idf.py monitor` (`Ctrl+]`), reset ESP32 или потеря
  master **не останавливают STM32 автоматически**. Отдельного slave-watchdog нет.
- `EEPROM_READY` отражает существующий флаг `i2c3_tx_wp`, не проверку содержимого
  EEPROM. После полного цикла проверить CRC и `*_rdy` через SWD после перезагрузки
  STM32. Ошибки базового алгоритма или I2C-драйвера этот интерфейс не исправляет.
