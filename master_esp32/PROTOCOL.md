# Протокол SNAP / STATUS / READ поверх RS-485 (Modbus-подобный, master=ESP32, slave=STM32)

Этот документ описывает, что было изменено в прошивке датчика (`Src/main.c`)
и как это соотносится со скетчем мастера `master_esp32.ino`.

## 1. Зачем нужен именно такой конвейер данных

Датчик считает угол непрерывно и асинхронно относительно опроса по шине:
АЦП защёлкивает новую строку пикселей, алгоритм считает по ней сектор/угол,
и так с частотой в десятки-сотни Гц. Мастер же обращается к шине сильно
реже и хочет получить **согласованный набор показаний от всех датчиков
на один и тот же момент времени** (например, для последующей триангуляции
по нескольким головкам). Если бы READ просто отдавал "текущее" значение
угла в момент запроса, то датчик 1 ответил бы данными за один физический
момент, а датчик 2 (опрошенный на несколько миллисекунд позже) — за другой,
и корреляция между головками была бы неверной.

Отсюда и трёхступенчатый буфер:

```
АЦП → расчёт → calculating → published → (SNAP,seq) → frozen + frozen_seq
```

* `calculating` — черновик текущего кадра, доступен только внутри одной
  итерации главного цикла, пока идёт расчёт.
* `published` — последний ПОЛНОСТЬЮ посчитанный кадр. Обновляется одним
  присваиванием структуры целиком, поэтому не бывает "разрыва" (угол уже
  новый, а sector ещё старый).
* `frozen` / `frozen_seq` / `frozen_ok` — неизменный снимок `published`,
  сделанный в момент прихода широковещательной команды `SNAP,seq`. Именно
  он живёт до следующего SNAP и just отдаётся по READ, независимо от того,
  что алгоритм в это время уже вовсю считает следующие кадры дальше.

Два отдельных шага STATUS и READ нужны потому, что:

1. RS-485 — полудуплексная шина, отвечать может только один участник за
   раз, поэтому SNAP не может быть с ответом (иначе на N датчиков будет
   N одновременных передатчиков и "каша" на линии).
2. Между широковещательным SNAP и опросом конкретного датчика проходит
   какое-то (небольшое) время. STATUS — это дешёвый, быстрый способ
   убедиться, что конкретный датчик действительно успел обработать SNAP
   именно с этим `seq`, прежде чем тратить время на более тяжёлый READ.
   Явный `NAK` вместо тишины экономит мастеру время (не нужно ждать
   полный таймаут).
3. По сценарию READ должен выполняться **только если ACK получен от всех
   датчиков** — иначе в наборе данных за `seq` образуется "дыра" от того,
   кто не успел, и весь набор для этого кадра нужно просто выбросить и
   подождать следующий цикл SNAP. Это уже логика мастера (см. `loop()`
   в `master_esp32.ino`), а не датчика.

## 2. Формат команд на линии (что реализовано в `Src/main.c`)

ASCII-строки, разделитель `,`, конец строки `\n` (необязательный `\r`
перед ним допускается и игнорируется — это уже было в исходном коде).

| Команда              | Кто шлёт | Кому               | Ответ                                              |
|----------------------|----------|--------------------|-----------------------------------------------------|
| `S,<seq>`             | мастер   | всем (broadcast)   | нет ответа                                          |
| `T,<id>,<seq>`        | мастер   | датчику `<id>`     | `ACK,<id>,<seq>,frame=<N>` или `NAK,<id>,<seq>`     |
| `R,<id>,<seq>`        | мастер   | датчику `<id>`     | `D,<id>,<seq>,angle_mdeg,sector,valid,state,frame`  |

Буква `T` выбрана для STATUS, потому что `S` уже занята под SNAP (как и
было в присланном скетче мастера), а `R` для READ уже использовалась в
исходном скетче (`requestReading()`/`parseData()`), формат `D,...` не
менялся, чтобы существующий парсер на ESP32 продолжал работать без
изменений.

Датчик игнорирует (ничего не отвечает в линию) команды `T`/`R` с чужим
`id` — это критично для многоточечной шины: если ответит "не тот"
датчик, это будет означать, что на линии одновременно кто-то ещё
попытается ответить/передать, и импульсы наложатся друг на друга.

## 3. Что именно изменено в `Src/main.c`

1. **`RS485_DEVICE_ID`** — адрес датчика на шине, задаётся на этапе сборки
   (`#define RS485_DEVICE_ID 1` по умолчанию, переопределяется флагом
   компилятора `-DRS485_DEVICE_ID=2` для второй прошивки). Для стенда на
   2 датчика соберите два разных .bin/.hex с ID=1 и ID=2.
2. **Скорость USART1 переведена с 9600 на 115200**, чтобы совпадать с
   `RS_BAUD` в скетче ESP32. Обязательно меняйте оба конца одновременно.
3. **Приём по RS-485 стал прерывание-управляемым**: раньше `USART1` в
   этой прошивке вообще не читался (только слался периодический "маяк"),
   входящих команд не существовало. Добавлены:
   * кольцевой буфер `rs485_rxbuf` + `USART1_IRQHandler()` — минимальная
     работа в прерывании (только положить байт в буфер);
   * `RS485_PollCommands()` — собирает байты из кольцевого буфера в
     строки по `\n` и вызывает `RS485_HandleLine()`; вызывается из
     `main()` на **каждой** итерации `while(1)`, а не только когда
     `adc_rdy==1`, чтобы не наследовать задержку от обработки кадра АЦП.
4. **Структура `Measurement` и конвейер `calculating → published →
   frozen`** — реализованы ровно так, как в задании. `published`
   пересчитывается на каждый обработанный кадр АЦП (`adc_rdy==1`), из
   тех же данных, что раньше уходили в `RS485_SendMeasurement()`
   (`errorflag`, `sector`, `rsector`, `cur_ang_E`, `encoder_state`).
5. **`RS485_OnSnap/OnStatus/OnRead`** — реализация команд протокола.
6. **Периодическая безадресная рассылка каждые 100 мс убрана**
   (`RS485_SendMeasurement()` больше не вызывается из `main()`). Это не
   просто "лишняя" функция — на общей шине с несколькими датчиками
   несколько передатчиков RS-485, одновременно поднимающих DE каждые
   100 мс, гарантированно устраивают на линии коллизии. Функция оставлена
   в файле (закомментированный вызов) только как заготовка для отладки
   одного датчика на столе в одиночку.

## 4. На что обратить внимание при переносе на реальное железо

1. **DE/RE на модуле RS-485.** В текущей схеме используется один
   GPIO (`RS485_DE_PIN`) и явно не видно отдельного RE. Код предполагает,
   что RE физически завязан на тот же сигнал (в инверсии), то есть пока
   идёт передача (DE=1), приёмник модуля отключён и не может "услышать"
   собственную передачу. Если на вашей плате RE управляется отдельно и
   всегда включён, то во время TX в `rs485_rxbuf` будет попадать эхо
   собственных байт — тогда нужно либо держать RE=0 на время TX
   отдельным GPIO, либо отбрасывать это эхо программно.
2. **Общий GND и терминаторы.** Стандартные требования для RS-485:
   витая пара A/B, терминирующие резисторы 120 Ом на обоих физических
   концах шины, общий GND между мастером и всеми датчиками.
3. **Бюджет времени на ответ.** `RS485_PollCommands()` вызывается в
   начале каждой итерации `while(1)`, но САМА обработка одного кадра АЦП
   (`if (adc_rdy == 1) {...}`) — блокирующая и может занимать заметное
   время (см. существующий счётчик `cycles_max`, снимаемый через
   `KIN1_GetCycleCounter()`). Пока идёт обработка кадра, входящие байты
   по-прежнему тихо копятся в кольцевом буфере по прерыванию, но
   РАЗБОР строки и ответ произойдут только на следующей итерации цикла,
   то есть с задержкой до "время обработки одного кадра". Перед тем как
   уменьшать `RESPONSE_TIMEOUT_MS` в скетче мастера ниже 30 мс, измерьте
   реальное время обработки кадра на вашем экземпляре платы (через
   `cycles_max` / осциллограф на DE) и убедитесь, что таймаут мастера
   заметно больше этого времени.
4. **Совпадение ID.** Если по ошибке два датчика прошиты одним и тем же
   `RS485_DEVICE_ID`, они будут отвечать на один и тот же `T`/`R`
   одновременно — коллизия. Стоит на первом этапе проверять каждый
   датчик по отдельности (физически отключив остальных от линии).
5. **Переполнение кольцевого буфера / порванные строки.** При обрыве
   связи или включении датчика посередине передачи возможна "хвостовая"
   мусорная строка без `\n` в начале сессии — `RS485_PollCommands()`
   просто отбрасывает такие строки целиком по превышению длины буфера
   строки, ничего страшного, следующая корректная строка обработается
   штатно.
6. **Дальнейшее развитие адресации.** Компиляция под конкретный ID на
   этапе сборки удобна для стенда на 2 датчика, но неудобна в
   производстве (нужно хранить N разных прошивок). Следующий шаг —
   читать адрес во время выполнения: DIP-перемычки на свободных GPIO,
   резисторный делитель на ADC-пине, либо значение в EEPROM (благо I2C
   EEPROM на плате уже используется под `ang_tab`/`buf_k`/`offset`, туда
   же можно добавить ещё одну ячейку под `device_id`).
7. **Целостность данных.** Текущий протокол, как и весь остальной обмен
   в проекте (SPI-фреймы уже используют CRC32), никак не защищён от
   искажения в линии — самое дешёвое усиление: добавить контрольную
   сумму (CRC8/16) в конец каждой строки и отбрасывать команды/ответы,
   которые не сошлись, вместо того чтобы полагаться только на "команда
   не распознана — игнорируем".

## 5. Логика мастера (`master_esp32.ino`)

* `sendSnap(seq)` — широковещательный `S,<seq>`, без ожидания ответа.
* `requestStatus(id, seq, &frame)` — `T,<id>,<seq>` с несколькими быстрыми
  повторами (`STATUS_RETRY_COUNT`), пока не придёт `ACK` именно с этим
  `id`/`seq` (тогда `true`) либо повторы не закончатся (`false`).
* `requestReading(id, seq, &out)` — `R,<id>,<seq>`, разбор `D,...` (код
  унаследован из присланного скетча один в один).
* `loop()`:
  1. SNAP всем.
  2. STATUS по очереди каждому ID из `SENSOR_IDS[]`.
  3. READ по очереди каждому ID — **только если ВСЕ STATUS вернули
     `true`**. Если хотя бы один датчик не подтвердил `seq`, READ для
     этого цикла целиком пропускается, и лог явно об этом сообщает.

`SENSOR_IDS[]` — единственное место, которое нужно менять для другого
количества датчиков (N), остальной код уже написан в виде циклов по
массиву, а не "захардкожен" под 2 головки.
