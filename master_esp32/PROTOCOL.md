# Протокол SNAP / STATUS / READ поверх RS-485, версия 2

Master — ESP32 (`master_esp32.ino`), slave — STM32F722 (`Src/main.c`).
Кодек строк общий для обеих сторон: [`Inc/rs485_proto.h`](../Inc/rs485_proto.h)
(копия для Arduino — `master_esp32/rs485_proto.h`, генерируется
`tools/sync_proto_header.sh`).

Разбор того, что и почему менялось в версии 2, — в [REPORT_v2.md](REPORT_v2.md).

> **Это не Modbus.** От Modbus взята только схема «один мастер, адресуемые
> слейвы, слейв не говорит первым». Здесь нет function codes, карты регистров,
> CRC-16 и межкадровых пауз 3.5 символа. Готовый Modbus-мастер с этой шиной
> работать не будет.

---

## 1. Зачем нужен именно такой конвейер

Датчик считает угол непрерывно и асинхронно опросу: АЦП защёлкивает строку
пикселей, алгоритм считает сектор и угол, и так десятки-сотни раз в секунду.
Мастер обращается к шине реже и хочет получить **согласованный набор показаний
от всех головок на один и тот же момент времени** (например, для триангуляции).
Если бы `READ` отдавал «текущее» значение, головка №1 ответила бы данными за
один физический момент, а головка №2, опрошенная на несколько миллисекунд
позже, — за другой.

Отсюда конвейер:

```
АЦП → расчёт → calculating → pub_buf[pub_idx] → (SNAP в прерывании) → frozen
```

* `calculating` — черновик текущего кадра, живёт внутри одной итерации главного цикла;
* `pub_buf[2]` + `pub_idx` — последний полностью посчитанный кадр; публикуется
  сменой индекса, потому что читает его **прерывание** (см. REPORT_v2, п.1);
* `frozen` — неизменный снимок, сделанный в момент приёма `SNAP`; именно он
  отдаётся по `READ`, пока алгоритм спокойно считает следующие кадры.

Два отдельных шага `STATUS` и `READ` нужны потому, что:

1. RS-485 полудуплексный — широковещательный `SNAP` не может иметь ответа,
   иначе N датчиков заговорят одновременно;
2. `STATUS` — дешёвая проверка «ты успел обработать именно этот `seq`?» до
   того, как тратить время на более длинный `READ`;
3. читать имеет смысл, только если готовы **все** головки, иначе набор за кадр
   всё равно неполный (эта логика — на мастере, в `loop()`).

## 2. Формат строки

```
<payload>*<CRC8 две hex-цифры><терминатор>
```

* разделитель полей — `,`;
* `CRC8` считается по всем символам `payload` (всё до `*`);
  полином **CRC-8/MAXIM** (0x31, reflected 0x8C, init 0x00) — тот же, что у
  `crc_table[]` в прошивке;
* терминатор — `\n` у команд мастера и `\r\n` у ответов слейва; обе стороны
  допускают необязательный `\r` и игнорируют его;
* всё ASCII, строка не длиннее `RS485_LINE_MAX` (64) байт.

### Команды мастера

| Команда | Кому | Ответ |
|---|---|---|
| `S,<seq>` | всем (broadcast) | нет ответа |
| `T,<id>,<seq>` | датчику `<id>` | `ACK,...` либо `NAK,...` |
| `R,<id>,<seq>` | датчику `<id>` | `D,...` либо `NAK,...` |

### Ответы слейва

| Ответ | Смысл |
|---|---|
| `ACK,<id>,<seq>,frame=<N>` | снимок под этот `seq` готов, это кадр номер `N` |
| `NAK,<id>,<seq>,<ПРИЧИНА>` | снимка нет, причина ниже |
| `D,<id>,<seq>,<angle_udeg>,<sector>,<valid>,<state>,<frame>` | данные снимка |

Причины `NAK`:

| Причина | Что произошло |
|---|---|
| `NOSNAP` | SNAP не приходил ни разу с момента включения датчика |
| `SEQ` | снимок есть, но под другой `seq` (этот SNAP потерян) |
| `STALE` | снимок под нужный `seq` протух по TTL |

Поля `D`:

| Поле | Тип | Диапазон |
|---|---|---|
| `angle_udeg` | целое | `0 … 359999999` микроградусов, либо `-1` = «угол неизвестен» |
| `sector` | целое | номер сектора, либо `-1` |
| `valid` | 0/1 | 1 — измерение достоверно (`errorflag==0`, сектора в диапазоне) |
| `state` | 2 hex | `encoder_state`, диагностика |
| `frame` | целое | свободно бегущий счётчик кадров головки |

`valid=1` обязано приходить с настоящим углом и сектором; комбинация
`valid=1` + `angle=-1` считается битой строкой и отбрасывается парсером.

### Примеры обмена

```
-> S,40001*35
-> T,1,40001*6F
<- ACK,1,40001,frame=90233*4A
-> T,2,40001*5B
<- ACK,2,40001,frame=88715*64
-> R,1,40001*21
<- D,1,40001,123456789,42,1,80,90233*0C
-> R,2,40001*15
<- D,2,40001,201333000,71,1,80,88715*77
```

Датчик **молча игнорирует** `T`/`R` с чужим `id` и любые строки, не прошедшие
CRC: на многоточечной шине лишний ответ — это коллизия.

## 3. Константы и инварианты

Все живут в `Inc/rs485_proto.h`, то есть меняются один раз для обеих сторон.

| Константа | Значение | Смысл |
|---|---|---|
| `RS485_RESPONSE_GUARD_MS` | 20 мс | слейв не отвечает на команду старше этого возраста |
| `RS485_MASTER_TIMEOUT_MS` | 30 мс | сколько мастер ждёт одну строку ответа |
| `RS485_FROZEN_TTL_MS` | 500 мс | после этого снимок протух (`NAK ... STALE`) |
| `RS485_EPOCH_IDLE_MS` | 500 мс | пауза, после которой SNAP с меньшим `seq` считается новой эпохой мастера |
| `RS485_ANGLE_SCALE` | 1 000 000 | единиц угла в градусе (микроградусы) |
| `RS485_LINE_MAX` | 64 | максимальная длина строки |

**Главный инвариант:** `RS485_RESPONSE_GUARD_MS < RS485_MASTER_TIMEOUT_MS` —
слейв замолкает раньше, чем мастер перестаёт слушать, иначе запоздавший ответ
наложится на следующую команду. Нарушение ловится на этапе компиляции
(`#error` в прошивке и `static_assert` в скетче).

Скорость — 115200 бод, 8N1, на обеих сторонах (`usart.BaudRate` в
`MX_RS485_USART1_Init()` и `RS_BAUD` в скетче).

## 4. Что происходит на слейве (`Src/main.c`)

| Событие | Где обрабатывается |
|---|---|
| приём байта | `USART1_IRQHandler()` → `RS485_RxByteFromISR()` |
| строка собрана (`\n`) | `RS485_LineFromISR()`: проверка CRC, разбор |
| `SNAP` | **в прерывании**, `RS485_SnapshotFromISR()` — это и есть общий момент «замри» |
| `STATUS`/`READ` своему `id` | кладутся в очередь с меткой времени |
| ответ | главный цикл, `RS485_PollCommands()` → `RS485_OnStatus()`/`RS485_OnRead()` |
| передача | прерывание TXE, DE снимается по TC |

Публикация кадра из главного цикла:

```c
uint8_t pub_next = rs485_pub_idx ^ 1U;
rs485_pub_buf[pub_next] = calculating;   /* заполняем свободный буфер */
__DMB();
rs485_pub_idx = pub_next;                /* публикация одной записью */
```

Диагностические счётчики — структура `rs485_stat` (смотреть отладчиком):
`rx_lines`, `crc_err`, `too_long`, `unknown`, `foreign`, `snap_ok`,
`snap_replay`, `q_overflow`, `guard_drop`, `tx_busy`, `ack_sent`, `nak_sent`,
`data_sent`.

Адрес на шине — `RS485_DEVICE_ID`, задаётся при сборке
(`-DRS485_DEVICE_ID=2` для второй головки).

## 5. Что происходит на мастере (`master_esp32.ino`)

```
loop():
  seq = ++nextSeq                       // старт nextSeq - esp_random()
  sendSnap(seq)                         // S,<seq>  broadcast, пауза 2 мс
  для каждого ID: requestStatus()       // T,<id>,<seq>, до 3 попыток
  если ВСЕ ответили ACK:
      для каждого ID: requestReading()  // R,<id>,<seq>, до 2 попыток
  выдержать период 100 мс
```

* ответы с несошедшейся CRC считаются помехой: мастер их считает и продолжает
  слушать до истечения таймаута;
* `NAK` разбирается с причиной и печатается в лог; повтор `READ` при `NAK` не
  делается (данных действительно нет), а при таймауте — делается;
* `SENSOR_IDS[]` — единственное место, которое нужно править под другое число
  датчиков.

## 6. На что обратить внимание на реальном железе

1. **DE/RE на модуле RS-485.** На STM32 используется один GPIO (`RS485_DE_PIN`),
   код предполагает, что `/RE` физически завязан на тот же сигнал. Если `RE`
   управляется отдельно и всегда включён, датчик будет слышать собственную передачу; с
   версии 2 это не ломает разбор (эхо не похоже на команду и просто поднимет
   счётчик `unknown`), но лучше завязать линии как положено.
2. **Общий GND и терминаторы.** Витая пара A/B, 120 Ом на обоих физических
   концах шины, общая земля между мастером и всеми датчиками.
3. **Окна с запрещёнными прерываниями.** `DMA2_Stream3_IRQHandler()` делает
   `__disable_irq()` и ждёт кадр TSL1401 опросом GPIO. Команды, пришедшие
   внутрь этого окна, теряются (ORE), строка штатно отбрасывается, мастер
   повторяет запрос. Это же окно — верхняя граница джиттера SNAP; подробности
   и варианты лечения в REPORT_v2, п.1.
4. **GPIO16/17 на ESP32-WROVER** заняты под PSRAM — UART2 там нужно перевесить
   на другие пины.
5. **Совпадение ID.** Два датчика с одинаковым `RS485_DEVICE_ID` ответят на
   один запрос одновременно. На первом этапе проверяйте головки по одной,
   физически отключив остальные.
6. **Точность угла.** Шесть знаков после запятой — разрядность формата. Тракт
   расчёта работает во `float`, поэтому реальный шаг около 360° — примерно
   30 микроградусов.

## 7. Миграция с версии 1

Версия 2 **несовместима** по формату: прошивать обе стороны нужно одновременно.

| | v1 | v2 |
|---|---|---|
| CRC | нет | `*XX` в конце каждой строки |
| угол | миллиградусы, `0…359999` | микроградусы, `0…359999999` или `-1` |
| `NAK` | только на `STATUS`, без причины | на `STATUS` и `READ`, с причиной |
| момент SNAP | главный цикл | прерывание приёма |
| передача слейва | блокирующая | по прерыванию, DE по TC |
| DE на ESP32 | `digitalWrite` + `flush()` | аппаратный RS-485 half duplex (RTS) |
| разбор | `sscanf`/`snprintf` | общий целочисленный кодек |
