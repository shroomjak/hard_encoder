## п.1 — снимок кадра в прерывании (главное изменение)

### Что было не так

В версии 1 путь команды `SNAP` выглядел так:

```
байт из линии -> USART1_IRQHandler() -> кольцевой буфер
                                             |
                       (ждём, пока главный цикл дойдёт до опроса)
                                             v
     main(): RS485_PollCommands() -> сборка строки -> sscanf -> RS485_OnSnap()
                                                                      |
                                                            frozen = published
```

То есть **момент фиксации данных определялся не приходом команды, а тем, когда
главный цикл в следующий раз доберётся до `RS485_PollCommands()`**. А главный
цикл в этот момент почти наверняка занят обработкой кадра АЦП:

```c
if (adc_rdy == 1)
{
    copy_data(); find_startpixel(); mes_piks(); find_datablock();
    calc_sector(); err_corr(); calc_ang(); find_avg(); offset_cal();
    angk_cal(); angtab_cal(); spi_SendExec(); dac_ctrl(); SloComProcess();
    ...
}
```

Этот блок блокирующий. Пока он не закончится, SNAP не обработается, хотя байты
команды давно лежат в буфере.

Почему это критично именно для этого протокола. Весь смысл команды SNAP — дать
всем головкам **один общий момент времени**, чтобы показания разных датчиков
можно было соотносить между собой (для той же триангуляции). Но:

* каждая головка крутит свой кадр АЦП асинхронно и в момент прихода SNAP
  находится в случайной фазе этого кадра;
* значит, задержка «команда → снимок» у головки №1 и у головки №2 **разная и
  случайная**, от нуля до полного времени обработки кадра;
* разброс между головками — это и есть ошибка синхронизации.

Численно: если обработка кадра занимает, скажем, 2 мс (реальное значение для
вашей платы смотрите в счётчике `cycles_max`, он считается через DWT), то две
головки могут сделать снимок с расхождением до 2 мс. При скорости вращения
60 °/с это 0.12° рассинхронизации — на пять порядков больше, чем разрешение,
которое мы теперь передаём по линии (шесть знаков после запятой). Протокол
обещал синхронность, а по факту давал «кто когда успел».

### Что сделано

Разбор строки и обработка SNAP перенесены **в сам обработчик прерывания**:

```c
void USART1_IRQHandler(void)
{
  if (RXNE) { RS485_RxByteFromISR(LL_USART_ReceiveData8(RS485_USART)); }
  ...
}

static void RS485_RxByteFromISR(uint8_t byte)      /* накапливаем строку */
{
    ...
    if (byte == '\n') { RS485_LineFromISR(rs485_isr_line, HAL_GetTick()); }
}

static void RS485_LineFromISR(char *line, uint32_t now)
{
    if (!rs485_strip_crc(line))      { crc_err++;  return; }   /* CRC */
    if (!rs485_parse_cmd(line, &cmd)) { unknown++; return; }   /* разбор */

    if (cmd.kind == RS485_CMD_SNAP) {
        RS485_SnapshotFromISR(cmd.seq, now);   /* <-- снимок ЗДЕСЬ И СЕЙЧАС */
        return;
    }
    ...                                        /* STATUS/READ -> в очередь */
}
```

Теперь задержка «последний байт SNAP → снимок» равна задержке входа в
прерывание плюс ~2–3 мкс на проверку CRC, разбор команды и копирование
структуры (при 216 МГц). Вместо миллисекунд — микросекунды, и, что важнее,
**одинаковые** для всех головок.

Обратите внимание на зависимость: обработка команды в прерывании стала
возможна только потому, что сначала был сделан п.5 — старый разбор через
`sscanf()` в ISR вызывать было нельзя (тяжёлый, тащит stdio, аллоцирует стек).

### Как теперь безопасно читать данные из прерывания

Появилась новая проблема: `published` пишет главный цикл, а читает прерывание,
которое может прийти в любой момент — в том числе посередине записи структуры.
Разберём варианты:

| Вариант | Почему не подошёл |
|---|---|
| Просто `frozen = published` | Прерывание может прийти посреди записи `published` в main → снимок «половина нового кадра, половина старого». |
| Seqlock (счётчик чётный/нечётный + повтор чтения) | **Deadlock.** Читатель здесь — прерывание, которое вытесняет писателя. Если ISR придёт, когда счётчик нечётный, он будет повторять чтение вечно: main не может продолжиться и закрыть запись, пока ISR не вернёт управление. |
| `__disable_irq()` вокруг публикации в main | Работает, но запрещает прерывания ровно в том коде, который должен срабатывать мгновенно, то есть возвращает джиттер, с которым мы боремся. |
| **Двойная буферизация (выбрано)** | Синхронизация не нужна вообще. |

Реализация:

```c
static Measurement      rs485_pub_buf[2];
static volatile uint8_t rs485_pub_idx;

/* писатель (main) */
uint8_t pub_next = rs485_pub_idx ^ 1U;
rs485_pub_buf[pub_next] = calculating;  /* пишем в СВОБОДНЫЙ буфер */
__DMB();
rs485_pub_idx = pub_next;               /* публикация одной записью байта */

/* читатель (ISR) */
idx = rs485_pub_idx;
__DMB();
frozen = rs485_pub_buf[idx];
```

Почему это корректно без единого критического участка:

* прерывание **не может быть вытеснено главным циклом** (Cortex-M: handler mode
  всегда приоритетнее thread mode), поэтому копирование в ISR никогда не
  прерывается записью из main;
* main пишет только в буфер, на который `pub_idx` не указывает, то есть никогда
  не трогает тот, что сейчас может читать ISR;
* публикация — одна запись однобайтовой переменной, она атомарна;
* `__DMB()` запрещает компилятору и ядру переставить публикацию индекса раньше
  заполнения буфера.

Цена вопроса — 16 лишних байт ОЗУ.

Чтение `frozen` в обратную сторону (из main, при формировании ответа) закрыто
коротким — десятки тактов — запретом прерываний в `RS485_FrozenCopy()`, иначе
ответ мог бы собраться из двух разных снимков.

### Что осталось за кадром (и это важно)

Прерывание USART1 имеет приоритет 5, но в прошивке есть участки с **глобально
запрещёнными прерываниями**. Главный из них — `DMA2_Stream3_IRQHandler()`
(приоритет 0), который делает `__disable_irq()` и внутри ждёт кадр TSL1401
опросом GPIO:

```c
__disable_irq();
SCB_InvalidateDCache_by_Addr(...);
while (!LL_GPIO_IsInputPinSet(GPIOC, LL_GPIO_PIN_6)) { }
while ( LL_GPIO_IsInputPinSet(GPIOC, LL_GPIO_PIN_6)) { }
...
__enable_irq();
```

Пока этот участок выполняется, USART1 не обслуживается. Поэтому честная
формулировка результата такая:

> Джиттер момента снимка больше не зависит от времени обработки кадра АЦП, но
> сверху ограничен длиной самого длинного окна с запрещёнными прерываниями.

Что с этим делать дальше (намеренно не стал трогать вслепую, без осциллографа —
это таймингозависимый код работы с TSL1401):

1. Измерить окно: дёрнуть свободный GPIO вокруг `__disable_irq()`/`__enable_irq()`
   и посмотреть осциллографом.
2. Если окно велико — заменить `__disable_irq()` на `__set_BASEPRI()` с порогом,
   который пропускает USART1, и поднять приоритет USART1 выше порога. Тогда
   RS-485 сможет вытеснять ожидание кадра. Проверять нужно на железе: опрос
   GPIO чувствителен к вытеснению.
3. Если нужна настоящая микросекундная детерминированность — выносить синхронизацию
   из протокола в железо: общая линия SYNC на все головки + таймерный захват,
   а RS-485 оставить только для вычитки данных.

Побочный эффект, который уже сейчас работает в плюс: байты, потерянные во время
такого окна, поднимают флаг ORE, а обработчик теперь помечает текущую строку
испорченной (`rs485_isr_drop = 1`), так что обрывок не разбирается, а честно
отбрасывается. Мастер получает таймаут и повторяет запрос.

## п.2 — контрольная сумма на каждой строке

**Было:** ни команды, ни ответы ничем не защищены. Одна помеха в поле угла — и
мастер принимал искажённое, но формально корректное число (проверялся только
диапазон). Для шины в цеху это не теория.

**Стало:** каждая строка заканчивается `*<CRC8 двумя hex-цифрами>`:

```
S,1234*7A
T,1,1234*63
ACK,1,1234,frame=987*1F
D,1,1234,123456789,42,1,80,987*2B
```

Полином выбран не случайный: это **CRC-8/MAXIM (poly 0x31, reflected 0x8C)** —
ровно то, что уже считает `crc_table[]`/`crc_8_step()` в прошивке. То есть
проект не обзавёлся вторым стандартом CRC, а переиспользовал имеющийся.
Совпадение проверяется автоматически (`tools/run_tests.sh`, шаг 2): скрипт
вытаскивает таблицу прямо из `Src/main.c` и сравнивает с полиномом кодека.

Строки с несошедшейся CRC: слейв молча отбрасывает (`rs485_stat.crc_err`),
мастер считает и печатает (`stats.crcErrors`), после чего продолжает слушать до
истечения таймаута — помеха не съедает ответ, который придёт следом.

Тест `test_crc_rejects_corruption` перебирает **все** односимвольные искажения
строки `D,...` и проверяет, что ни одно не проходит через CRC и парсер.

## п.3 — guard time на ответе слейва

**Было:** слейв отвечал на команду всегда, независимо от того, сколько времени
прошло. Если главный цикл задержался дольше мастерского таймаута (30 мс),
ответ уходил в линию уже после того, как мастер бросил ждать и начал передавать
следующую команду, — то есть ровно в момент чужой передачи. На полудуплексной
шине это коллизия: портятся обе посылки.

**Стало:** каждая команда кладётся в очередь вместе с меткой времени приёма
(`HAL_GetTick()` в прерывании), а главный цикл перед ответом проверяет возраст:

```c
if ((HAL_GetTick() - cmd.tick) > RS485_RESPONSE_GUARD_MS) {
    rs485_stat.guard_drop++;
    continue;                   /* опоздали - молчим */
}
```

Инвариант «слейв замолкает раньше, чем мастер перестаёт слушать» зафиксирован в
общем заголовке и проверяется на этапе компиляции с обеих сторон:

```c
/* Src/main.c */
#if RS485_RESPONSE_GUARD_MS >= RS485_MASTER_TIMEOUT_MS
#error "RS485_RESPONSE_GUARD_MS must be strictly less than RS485_MASTER_TIMEOUT_MS"
#endif

/* master_esp32.ino */
static_assert(RS485_RESPONSE_GUARD_MS < RS485_MASTER_TIMEOUT_MS, "...");
```

Текущие значения: guard 20 мс, таймаут мастера 30 мс (`Inc/rs485_proto.h`).
Менять нужно только там — обе стороны подхватят.

## п.4 — время жизни снимка и «эпоха» мастера

**Было:** `frozen_ok` выставлялся один раз и больше никогда не сбрасывался.
Сценарий отказа: мастер перезагрузился и начал нумерацию заново с `seq=1`.
Если его `SNAP,1` до датчика не дошёл (помеха, окно с запрещёнными
прерываниями), а у датчика в `frozen_seq` с прошлой сессии лежит та же `1`, то
на `STATUS,id,1` он ответит бодрым `ACK` — и отдаст данные **прошлой сессии**,
снятые неизвестно когда.

**Стало** — три независимых барьера:

1. **TTL снимка.** Снимок старше `RS485_FROZEN_TTL_MS` (500 мс, пять циклов
   опроса) считается протухшим, ответ — `NAK,id,seq,STALE`:
   ```c
   if ((HAL_GetTick() - ftick) > RS485_FROZEN_TTL_MS) return RS485_NAK_STALE;
   ```
2. **Монотонность seq с учётом эпохи.** Нормальным считается `seq` строго
   больше предыдущего. Меньший или равный принимается, только если SNAP не
   приходил дольше `RS485_EPOCH_IDLE_MS` (значит, мастер перезапустился):
   ```c
   if (frozen_ok &&
       ((int32_t)(seq - rs485_last_snap_seq) <= 0) &&
       ((now - rs485_last_snap_tick) < RS485_EPOCH_IDLE_MS)) {
       rs485_stat.snap_replay++;   /* дубль или реплей - игнорируем */
       return;
   }
   ```
   Сравнение через `(int32_t)(a - b)` корректно работает и на переполнении
   32-битного счётчика.
3. **Случайный старт нумерации на мастере.** `nextSeq = esp_random() & 0x7FFFFFFF`
   — вероятность, что после перезагрузки мастер попадёт ровно в тот `seq`,
   который датчик помнит с прошлой сессии, около 2⁻³¹. Формат строки при этом
   не меняется: «эпоха» спрятана в самом номере.

Самовосстановление: если после перезагрузки мастера его случайный `seq`
оказался меньше запомненного, первые несколько SNAP будут отвергнуты как
реплей, датчик ответит `NAK,...,SEQ`, а через `RS485_EPOCH_IDLE_MS` тишины
(отвергнутые SNAP таймер эпохи не обновляют) всё заработает штатно.

## п.5 — микроградусы и отказ от sscanf/snprintf

Два изменения в одном пункте.

### Единицы угла: миллиградусы → микроградусы

На линии угол теперь целое число микроградусов, диапазон `0 … 359 999 999`,
плюс отдельное значение `-1` — «достоверного угла ещё не было ни разу»:

```
D,1,1234,123456789,42,1,80,987*2B     ->  123.456789 градуса
```

Мастер печатает его с шестью знаками: `A=123.456789`.

Заодно убран костыль версии 1. Там парсер мастера жёстко требовал
`0 ≤ angle < 360000` и выбрасывал строку целиком, поэтому при невалидном
измерении слейв был вынужден слать последний нормальный угол, даже если
валидных измерений не было вообще (и слал ноль). Теперь `-1` — легальное
значение, но только вместе с `valid=0`; комбинация «valid=1 и угол неизвестен»
парсером отвергается как заведомо битая строка.

> **Честно о точности.** Шесть знаков — это разрядность *формата*, а не
> внезапно выросшая точность датчика. `cur_ang_E` — `float`, 24 бита мантиссы,
> поэтому шаг представимых значений около 360° составляет примерно
> 3·10⁻⁵ градуса (~30 микроградусов). Последние 1.5 знака из шести — шум
> представления. Чтобы они стали настоящими, в `double` нужно переводить весь
> тракт расчёта (`calc_ang`, `ang_tab`, `offset`, калибровки), а не формат
> вывода; на Cortex-M7 с одинарным FPU это заметная переделка и отдельная
> работа. Сейчас же формат как минимум перестал быть узким местом.

Само преобразование сделано без `double` (на M7 он эмулируется программно) и
без libm: целая и дробная части считаются раздельно, результат зажимается в
допустимый диапазон, NaN и выход за 360° обрабатываются явно —
`RS485_AngleToMicro()`.

### Долой stdio из тракта RS-485

Было: `sscanf()` на разбор команд и `snprintf()` (с `%f` в отладочной выдаче)
на формирование ответов. Это десятки килобайт библиотеки, сотни тактов на
строку, нетривиальный расход стека — и всё это принципиально нельзя было
вызывать из прерывания, то есть п.1 был бы невозможен.

Стало: общий кодек `Inc/rs485_proto.h` на целочисленной арифметике —
writer, который физически не может выйти за границы буфера, и строгий
парсер, отвергающий любое лишнее поле, лишний символ или переполнение
`uint32`. Ни одного вызова stdio в тракте RS-485 не осталось.

Дополнительный выигрыш: **кодек один и тот же на обеих сторонах шины**. Раньше
формат строки существовал в двух независимых реализациях (`snprintf` в
прошивке и `sscanf` в скетче), и любое расхождение вылезло бы только на стенде.

## п.6 — неблокирующая передача

**Было:**

```c
LL_GPIO_SetOutputPin(RS485_PORT, RS485_DE_PIN);
for (i = 0; i < len; i++) {
    while (!LL_USART_IsActiveFlag_TXE(RS485_USART)) { }   /* ждём */
    LL_USART_TransmitData8(RS485_USART, data[i]);
}
while (!LL_USART_IsActiveFlag_TC(RS485_USART)) { }        /* ждём */
LL_GPIO_ResetOutputPin(RS485_PORT, RS485_DE_PIN);
```

Строка `D,...` — это 55 байт, на 115200 бод около **4.8 мс**, в течение которых
главный цикл не делает ничего. При опросе 10 раз в секунду это до 5% времени
процессора, выброшенного в ожидание, и ровно столько же добавки к задержке
обработки следующего кадра АЦП.

**Стало:** строка копируется в буфер, DE поднимается, включается прерывание
TXE — и управление сразу возвращается в главный цикл. Байты выдаёт ISR, а DE
снимается строго по флагу **TC** (не TXE — иначе последний символ обрежется на
середине):

```c
if (TXE) {
    if (rs485_tx_pos < rs485_tx_len) { TransmitData8(buf[rs485_tx_pos++]); }
    else { DisableIT_TXE(); EnableIT_TC(); }      /* данные кончились, ждём TC */
}
if (TC) {
    DisableIT_TC(); ClearFlag_TC();
    ResetOutputPin(DE);                            /* отпускаем шину */
    rs485_tx_busy = 0;
}
```

Протокол строго «запрос-ответ», поэтому наложения двух передач быть не может;
на всякий случай попытка начать передачу при занятом передатчике не ломает
ничего, а считается в `rs485_stat.tx_busy` (мастер отработает таймаут и
повторит).

Блокирующая обёртка `RS485_Write()` сохранена — ею пользуются только отладочные
`RS485_Test()`/`RS485_SendMeasurement()`, которые в рабочем режиме не вызываются.

## п.7 — аппаратное управление DE на ESP32

**Было:**

```c
digitalWrite(RS_DE, HIGH);
Serial2.write(...);
Serial2.flush(true);
digitalWrite(RS_DE, LOW);
```

Проблема в `flush()`: в зависимости от версии arduino-esp32 он ждёт опустошения
программного буфера и FIFO, но не обязательно — ухода последнего бита из
сдвигового регистра. Снятый на полсимвола раньше DE = обрезанный последний
символ в линии; ловится такое отвратительно (плавает, зависит от загрузки).

**Стало:** направлением управляет сама периферия UART — режим RS-485
half-duplex, DE висит на линии RTS:

```c
Serial2.begin(RS_BAUD, SERIAL_8N1, RS_RX, RS_TX);
uart_set_pin(RS_UART, RS_TX, RS_RX, RS_DE, UART_PIN_NO_CHANGE);  /* RTS = DE */
uart_set_mode(RS_UART, UART_MODE_RS485_HALF_DUPLEX);
```

Контроллер сам поднимает DE перед первым битом и снимает после последнего,
программной гонки не существует. Заодно в этом режиме приёмник отключён на
время передачи, то есть мастер не слышит собственное эхо.

Программный путь оставлен под `#define RS485_HW_DE 0` — на случай старого ядра
без `uart_set_mode()`. Но и он исправлен: вместо `flush()` вызывается
`uart_wait_tx_done()`, который ждёт именно полного ухода кадра. Обе ветки
проверяются компиляцией в `tools/run_tests.sh`.

## п.9 — NAK вместо молчания на READ

**Было:** если снимка под запрошенный `seq` нет, слейв на `READ` просто молчал.
Мастер при этом обязан был отсидеть весь таймаут (30 мс) на каждом таком
запросе, хотя ответ «данных нет» был известен датчику мгновенно. На `STATUS`
при этом `NAK` уже был — несимметрично.

**Стало:** `READ` отвечает `NAK,<id>,<seq>,<ПРИЧИНА>`, причём с конкретной
причиной, одинаковой для `STATUS` и `READ`:

| Причина | Что означает |
|---|---|
| `NOSNAP` | SNAP вообще не приходил с момента включения датчика |
| `SEQ` | Снимок есть, но под другой `seq` (этот SNAP потерян) |
| `STALE` | Снимок под нужный `seq` есть, но протух по TTL |

Мастер разбирает причину, печатает её в лог и не повторяет READ (повтор при
явном отказе бессмыслен) — в отличие от таймаута, где повтор как раз делается.
При диагностике стенда это сразу отвечает на вопрос «почему нет данных»:
`NOSNAP` — не доходят широковещательные команды, `SEQ` — теряется конкретный
SNAP, `STALE` — датчик отвечает слишком медленно.

## Что осталось непроверенным и честные ограничения

1. **Железо не тестировалось.** В песочнице нет ни ARM-тулчейна (проект
   собирается IAR), ни Arduino-окружения, ни самой платы. Проверено всё, что
   можно проверить на хосте: логика кодека юнит-тестами, компилируемость обеих
   сторон (gcc/g++ с заглушками LL/HAL и Arduino/IDF, `-Wall -Wextra -Werror`).
   Работа с регистрами USART и реальные тайминги шины проверяются только на
   стенде.
2. **Остаточный джиттер SNAP** ограничен окнами с глобально запрещёнными
   прерываниями в `DMA2_Stream3_IRQHandler()` — см. конец раздела п.1. Это
   следующий по важности шаг, но он требует осциллографа.
3. **Шесть знаков угла — формат, а не точность.** Реальное разрешение
   ограничено `float` в тракте расчёта (~30 микроградусов у верхней границы
   диапазона).
4. **Адрес датчика по-прежнему задаётся на этапе сборки** (`-DRS485_DEVICE_ID=2`).
   Два разных бинаря на две головки. Переход на runtime-адрес (DIP, делитель на
   ADC, ячейка в EEPROM) не входил в задачу.
5. **CRC-8 — защита от помех, не от злоумышленника.** Для шины внутри прибора
   этого достаточно; для длинных линий с тяжёлыми наводками имеет смысл
   перейти на CRC-16 (стоимость — одна строка в кодеке).
6. **Guard time 20 мс грубоват**, потому что опирается на `HAL_GetTick()` с
   шагом 1 мс. Если понадобится ужать цикл опроса, метку времени стоит снимать
   счётчиком тактов DWT (он в прошивке уже включён) — это даст доли микросекунды.
7. **Кодировки файлов в репозитории смешанные.** `*.c/*.h` — CP1251 (так
   настроено в `.gitattributes`/`.editorconfig`), скетч и документация — UTF-8.
   Копия кодека для Arduino генерируется `tools/sync_proto_header.sh`, а их
   расхождение ловит `tools/run_tests.sh`. Приводить весь проект к UTF-8 я
   намеренно не стал — это отдельная массовая правка, которая замусорит diff
   этого PR.

## Как проверить

### На хосте (прямо сейчас, без железа)

```bash
./tools/run_tests.sh
```

Шесть проверок:

1. копии `rs485_proto.h` для прошивки и для скетча совпадают;
2. `crc_table[]` в `Src/main.c` — это ровно CRC-8/MAXIM, который считает кодек;
3. кодек компилируется как C99 (прошивка) без предупреждений;
4. кодек компилируется как C++11 (скетч) и проходит 89 юнит-проверок, включая
   перебор всех односимвольных искажений строки данных;
5. RS-485 часть `Src/main.c` компилируется с заглушками LL/HAL;
6. `master_esp32.ino` компилируется с заглушками Arduino/IDF в обоих вариантах
   управления DE.

### На стенде

1. Собрать прошивку дважды: по умолчанию `RS485_DEVICE_ID=1`, для второй
   головки `-DRS485_DEVICE_ID=2`.
2. Проверять по одному датчику на линии, физически отключив остальные.
3. В мониторе порта ждать строки вида
   `seq=… ID1:ACK(frame=…) ID2:ACK(frame=…) | ID1 A=123.456789 S=42 V=1 ST=80 F=…`
   и раз в 50 циклов — строку `[стат] …` с числом таймаутов, ошибок CRC и NAK.
4. При проблемах смотреть отладчиком структуру `rs485_stat` в прошивке:

| Поле | О чём говорит рост |
|---|---|
| `crc_err` | помехи на линии, нет терминаторов 120 Ом, плохая земля |
| `too_long` | мусор в линии или рассинхрон скорости |
| `foreign` | команды к другому ID (норма на многоточечной шине) |
| `snap_replay` | мастер повторяет seq или перезагружался |
| `guard_drop` | главный цикл не успевает ответить в отведённые 20 мс |
| `q_overflow` | команды приходят быстрее, чем главный цикл их разбирает |
| `tx_busy` | нарушена дисциплина «запрос-ответ» на шине |
