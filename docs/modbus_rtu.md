# Modbus RTU: головки STM32F722 и ведущий контроллер ESP32

Здесь описаны **два самостоятельных проекта прошивки**. Головки с STM32F722 — подчинённые устройства (slave), ESP32 — ведущее устройство (master) на общей двухпроводной шине RS485. У каждой головки собственный адрес Modbus. Контакты отладчика STM32 и порт RS485 выполняют разные функции.

## 1. Какие библиотеки нужны

| Устройство | Протокольный стек | Где находится и как подключается |
|---|---|---|
| STM32 | [FreeModbus](https://github.com/cwalter-at/freemodbus) Christian Walter, версия на коммите `a9ec789a23ff774287e711aeb18492860c8770cf`, лицензия BSD 3-Clause | Нужные исходные файлы **уже добавлены** в `ThirdParty/FreeModbus/` вместе с `LICENSE`. Дополнительно скачивать их не нужно. Настройки — `ThirdParty/FreeModbus/include/mbconfig.h`, аппаратная адаптация — `Inc/port.h` и `Src/modbus_port.c`, регистры — `Src/modbus_registers.c`. Всё включено в `EWARM/taos.ewp`. Драйверы HAL/LL/CMSIS уже лежат в `Drivers/`. |
| ESP32 | Официальный компонент Espressif [esp-modbus](https://github.com/espressif/esp-modbus), версия **2.1.4**, лицензия Apache-2.0 | `esp32_master/main/idf_component.yml` предписывает менеджеру компонентов ESP-IDF скачать библиотеку при первой сборке. Нужны установленный **ESP-IDF 5.x** (компонент заявляет совместимость с IDF ≥ 5.0), доступ к менеджеру компонентов и его зависимостям. Библиотеку не следует вручную копировать в `Src` проекта STM32. |

Оба стека выполняют кадрирование Modbus RTU и контроль CRC16; прикладной код реализует адаптацию STM32, фиксацию/опрос и командный мост калибровки. В FreeModbus добавлены две локальные правки: запрет broadcast кроме FC06 holding[0] (SNAP) и преобразование MB_EINVAL в exception 03. Сгенерированные каталоги ESP-IDF `build/` и `managed_components/` не входят в репозиторий. Существующий `Src/main.c` исторически сохранён в **Windows-1251 (CP1251)**. **Новые** файлы интерфейса STM32 (`Src/modbus_*.c`, `Src/snapshot_registers.c`, `Src/encoder_calibration.c` и их заголовки), проект ESP32 и эта документация сохранены в **UTF-8**, чтобы русские комментарии читались в GitHub. Эти исключения прописаны в `.editorconfig`; для старого `Src/main.c` при необходимости выбирайте CP1251 в редакторе.

## 2. Как прошить ESP32: ESP-IDF, USB, а не IAR

**IAR EWARM (`EWARM/taos.ewp`) предназначен для прошивки головок STM32.** Файл `esp32_master/main/main.c` — точка входа `app_main()` **другого проекта**, собираемого **ESP-IDF**; его нельзя добавить в проект IAR STM32 и прошить через отладочный порт головки. Можно работать из командной строки ESP-IDF или через расширение Espressif IDF для VS Code, которое вызывает те же инструменты.

### Оборудование и кабели

* Для обычной отладочной платы **классической ESP32**: подключить её USB-разъём **кабелем с передачей данных** к компьютеру. Обычно на такой плате USB подключён к преобразователю **USB↔UART0**: по нему загрузчик принимает прошивку, затем в том же порту видны сообщения `ESP_LOGI/W/E`. Это **не** тот UART, который отправляет Modbus-запросы: пример использует `UART_NUM_2` на GPIO17/16/4.
* Если на плате нет USB-разъёма или USB↔UART-преобразователя, нужен отдельный **USB↔UART-адаптер уровня 3,3 В** на загрузочный UART ESP32 и предусмотренное схемой управление `EN`/`GPIO0` (или ручной вход в режим загрузчика). Нельзя подавать 5 В на сигнальные выводы ESP32. Конкретные подключения питания и режима загрузки сверять со схемой своей платы.
* У ESP32-S2/S3/C3 и некоторых других моделей может быть собственный USB или USB Serial/JTAG: там способы загрузки, доступность `UART_NUM_2` и номера GPIO **отличаются**. Этот пример и команды `set-target esp32` рассчитаны именно на классическую ESP32. Для другой модели сначала заменить целевой чип в ESP-IDF, проверить доступные UART/GPIO и отладочную консоль.
* **USB сам по себе не является RS485.** Для работы программы дополнительно нужен преобразователь UART↔RS485 на стороне ESP32 и подключение A/B к головкам. USB нужен для прошивки и просмотра журнала; аппаратный разъём TCK/TMS/SWO/NRST на STM32 нужен для программирования/отладки **STM32**, не ESP32.

### Порядок действий

1. Установить ESP-IDF 5.x и открыть настроенный терминал ESP-IDF (в Windows — установленный ESP-IDF Command Prompt/PowerShell, в Linux/macOS — терминал после выполнения `. <путь-к-esp-idf>/export.sh`). Проверить `idf.py --version`. Для установки IDF пользоваться [официальным руководством Espressif](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/get-started/index.html).
2. В `esp32_master/main/main.c` сверить `MB_TX_GPIO`, `MB_RX_GPIO`, `MB_RTS_GPIO` с **реальной** разводкой ESP32 ; список головок теперь задаётся в консоли (`poll 1,2`). На двух головках STM32 должны быть разные `MB_SLAVE_ADDRESS` в `Inc/modbus_board.h` (1 и 2 в примере). Подключить RS485, общий провод GND и питание согласно схемам плат.
3. Перейти в каталог `esp32_master` и **один раз для этого проекта** выбрать классическую ESP32:

   ```sh
   cd esp32_master
   idf.py set-target esp32
   idf.py build
   ```

   `idf.py build` компилирует `main/main.c` (с функцией `app_main()`), сам компонент Modbus и остальные части проекта ESP-IDF; прошивка получается из **всего проекта**, а не из одного файла `main.c`. IDF подготовит приложение и служебные образы загрузчика/таблицы разделов. При первой сборке менеджер компонентов загрузит `espressif/esp-modbus` версии 2.1.4. При отсутствии доступа к его серверу сборка не сможет получить компонент; понадобится настроенный заранее кэш/локальная установка компонента с его зависимостями.
4. Определить USB-порт платы: например `COM5` в Windows («Диспетчер устройств»), `/dev/ttyUSB0` или `/dev/ttyACM0` в Linux, `/dev/cu.usbserial-...` в macOS. Имя порта и при переподключении платы может измениться. Записать **собранную прошивку ESP32** и открыть последовательный монитор:

   ```sh
   idf.py -p COM5 flash monitor          # Windows: подставить свой COM-порт
   # либо, например, в Linux:
   idf.py -p /dev/ttyUSB0 flash monitor
   ```

   `flash` загружает **собранные образы** через USB-загрузчик платы, `monitor` отображает сообщения `SNAP`, `ACK`, `DATA` и ошибки. После ввода `poll 1,2` сразу начинается рабочий опрос, без поиска адресов. При двух исправных головках порядок сообщений примерно такой: `SNAP seq=42`, `ACK id=1 seq=42`, `ACK id=2 seq=42`, затем два сообщения `DATA ...`. Если одна головка не ответила, появится предупреждение о пропуске всех READ. По умолчанию консоль проекта ESP-IDF обычно использует 115200 бод на загрузочном UART; **115200/8E1 шины Modbus — отдельная настройка UART2**. Для выхода из монитора ESP-IDF нажать `Ctrl+]`.
5. Если при загрузке появляется `Connecting...` и подключение не устанавливается: убедиться, что USB-кабель передаёт данные и установлен драйвер USB↔UART платы; при отсутствии автоматического управления загрузкой удерживать **BOOT** (`GPIO0`), кратко нажать **EN/RESET**, затем отпустить BOOT после входа в режим загрузки. В Linux проверить права доступа к последовательному порту (обычно группа `dialout` или аналогичная); закрыть другие программы, занявшие этот порт. Успешная загрузка ESP32 ещё не подтверждает работоспособность RS485: отдельно проверять соединения A/B, направление DE и адреса головок.

> **Управление после загрузки:** в `idf.py monitor` появится `encoder>`.
> Введите `poll 1,2` или `calib 2,1`: эти команды **не запускают scan**.
> Без списка ID используется кэш завершённого ручного поиска; если кэш пуст,
> нужно указать ID или выполнить `scan`. Кэш не сохраняется после reboot;
> новый `scan` заменяет его, отменённый поиск оставляет пустой кэш.
> `scan` — ручной поиск адресов 1..247 (около двух минут), без запуска режима;
> `next` — подтверждение этапа/следующей головки;
> `stop` — остановка выбранного режима. После reboot программа ждёт команду.
> Это команды UART0-консоли прошивки, не параметры утилиты `idf.py`.
> [Подробная инструкция и меры безопасности](../esp32_master/README.md#команды-в-idfpy-monitor).

## 3. Прошивка и подключение STM32

Головку STM32 собирают и отлаживают в **IAR EWARM** через совместимый отладчик, подключённый к её SWD/JTAG-контактам (`TCK/SWCLK`, `TMS/SWDIO`, сброс; `SWO/TDO` — если применимы). Отладочный интерфейс не заменяет линию RS485. В `EWARM/taos.ewp` уже прописаны новые исходники FreeModbus, пути заголовков и переносимая ссылка на драйвер LL USART. Для разных головок изменить `MB_SLAVE_ADDRESS`, пересобрать и прошить каждую отдельно. Перед проверкой связи выполнить аппаратную проверку пинов по следующему разделу.

## 4. Проводное подключение и настройки последовательных портов

Оба конца используют **Modbus RTU, 115200 бод, 8 бит данных, чётная чётность, 1 стоп-бит (8E1), двухпроводный полудуплексный RS485**.

**Схема именно этой платы STM32 в репозитории отсутствует.** Файл `taos.ioc` не описывает RS485. `Inc/modbus_board.h` содержит только **пример**, не проверенную разводку: USART1 PB6=TX → DI преобразователя, PB7=RX ← RO, PB5=DE (активен при 1), PB4=/RE (приём разрешён при 0); TIM2 отсчитывает паузу между кадрами Modbus. До прошивки проверить по электрической схеме фактические выводы USART, AF, DE и /RE и отсутствие конфликта с другими функциями. При другом USART нужно изменить также привязку периферии/IRQ/тактовой частоты в `Src/modbus_port.c`: заменить только макросы пинов недостаточно. Контакты PA13/PA14/PB3 отладчика не переназначаются.

В примере **классической ESP32** `esp32_master/main/main.c` использует GPIO17 (UART2 TX → DI), GPIO16 (UART2 RX ← RO), GPIO4 (UART2 RTS → DE и /RE). `uart_set_mode(..., UART_MODE_RS485_HALF_DUPLEX)` управляет переключением направления через RTS. Если DE и /RE раздельные или имеют иную схему управления, согласовать соединения с преобразователем и скорректировать код; не связывать напрямую несогласованные выходы. На A/B обеспечить общий GND, согласование 120 Ом на **концах** кабеля и резисторы смещения в одной точке, если они не предусмотрены преобразователями. Сигналы GPIO ESP32 — уровня 3,3 В.

У каждой головки должен быть **уникальный** Modbus-адрес 1..247 (`MB_SLAVE_ADDRESS`); адрес 0 зарезервирован для вещания. В примере прошить первую головку с адресом 1, вторую с 2. Если адреса совпадают, оба slave ответят одновременно — на RS485 будет коллизия. Сейчас адрес задаётся при компиляции, а не через USB или запрос Modbus. Для серийного изделия можно отдельно реализовать установку адреса через EEPROM/перемычки.

## 5. Команды и порядок опроса

В псевдокоде пользователя `SNAP`, `STATUS`, `READ` — это **не новые функции Modbus**. Они отображены на стандартные запросы:

| Действие | Запрос Modbus RTU | Что получает ведущий контроллер |
|---|---|---|
| `SNAP(seq=42)` | Адрес устройства **0**, функция **06** (запись одного регистра хранения), адрес регистра **0**, значение `42` | **Нет ответа:** Modbus запрещает ответы на вещательный запрос. Каждая головка сохраняет последний полностью обработанный кадр. Повтор того же `seq` при `ready=1` не заменяет снимок. |
| `STATUS(id,42)` | Адрес **id**, функция **04** (чтение входных регистров), адреса **0..1** | `seq`, `ready`. Считать подтверждением только совпадение `seq` и `ready=1`. |
| `READ(id,42)` | Адрес **id**, функция **04**, адреса **0..10** | Все сохранённые данные; повторно проверить `seq` и `ready` в ответе. Запрашивается, только если подтвердили **все** головки. |

FreeModbus вызывает прикладные обработчики с адресом регистра **на 1 больше адреса на линии**: запись по адресу 0 приходит в `eMBRegHoldingCB()` как `address=1`. `Src/modbus_registers.c` учитывает это смещение. Кадрирование, адресацию, CRC16 и паузу тишины t3.5 выполняет библиотека; STM32 отпускает линию (DE=0) только после передачи последнего стоп-бита по флагу TC. Непрошеных ответов от slave нет.

Номер `seq` — 16-битный счётчик ведущего контроллера. В демонстрации он начинается с 42, увеличивается при каждом цикле и переполняется после 65535. Если ведущий контроллер перезагрузить и начать снова с того же `seq`, подчинённое устройство может принять его за повтор уже подтверждённого кадра. В рабочем изделии хранить следующий `seq` в энергонезависимой памяти (NVS) или предусмотреть иной механизм исключения старого подтверждения. Успешная отправка вещательного запроса **не означает**, что его приняли все: поэтому контроллер отдельно проверяет STATUS каждой головки. Если хотя бы одна не подтвердила запись, весь этап READ пропускается; при ошибке STATUS выполняется одна повторная попытка. Библиотека ESP32 выдерживает после вещания заданную задержку (в примере 150 мс).

### Карта входных регистров функции 04

Адреса указаны **с нуля на линии**, а не в справочном формате «3xxxx/4xxxx». Каждое поле регистра — 16 бит; для 32-битных полей сначала передаётся старшее слово.

| Адрес | Содержимое |
|---|---|
| 0 | `seq`: номер последнего SNAP, даже если результат оказался невалидным. |
| 1 | `ready`: 1, если обработан хотя бы один кадр, `errorflag=0`, сектор `<144`, угол в `[0,360)`; иначе 0. |
| 2–3 | Угол в **микроградусах**, `uint32` (1° = 1000000; например, 90,500000° = 90500000). |
| 4 | Номер сектора. |
| 5 | `errorflag` алгоритма декодирования. |
| 6 | `encoder_state` — состояние алгоритма калибровки из существующего ПО. |
| 7–8 | Порядковый номер обработанного кадра АЦП, `uint32`. |
| 9–10 | Локальное время головки `HAL_GetTick()`, мс, `uint32`. Часы разных головок **не синхронизированы**. |

Угол переводится из `float` в градусах в `uint32` микроградусов в
`snapshot_publish()`: умножение на 1000000 выполняется в `double`, затем
округление до ближайшего целого (половина вверх). Исходный угол проверяется
на диапазон `[0,360)`; NaN, бесконечность и ошибочные кадры дают `ready=0`.
Микроградусы задают формат хранения и передачи, но не повышают точность
исходного вычисления в `float`. Master собирает слова 2–3 и выводит градусы
с шестью знаками после запятой, деля целую часть на 1000000 и используя
остаток как дробную часть.

**Несовместимое изменение масштаба:** карта из 11 регистров не изменилась,
но угол теперь в 1000 раз больше прежнего значения в миллиградусах.
Обновлять прошивки STM32 slave и ESP32 master нужно вместе: поле версии
или автоматическое определение масштаба в протоколе отсутствует.
Действующий проект ESP-IDF собирает `esp32_master/main/main.c` и
`esp32_master/main/workflow.c`. Общие адреса команд — `Inc/encoder_protocol.h`.

Массив `buf_x0[128]` **не передаётся**: DMA продолжает изменять пиксели, а сценарий считывания угла в них не нуждается. Для сырого изображения потребуется отдельный замороженный массив и выдача несколькими запросами: 128 × 16 бит не помещаются в один ответ Modbus RTU.

Обработка `SNAP` происходит в основном цикле при `eMBPoll()`, а не в прерывании в физический момент фронта на A/B. Каждая головка сохраняет последний **завершённый** результат на момент обработки команды; строго одновременной экспозиции разных головок это не гарантирует. Для субмиллисекундной синхронизации необходим отдельный общий аппаратный сигнал запуска.

## 6. Проверки и границы подтверждённого результата

```sh
python3 tests/sector_decode_test.py
sh tests/host/run_snapshot_test.sh   # сохранение снимка и границы регистров
sh tests/host/run_rtu_test.sh        # FreeModbus RTU, CRC, вещание и функция 04
```

Хостовые тесты пройдены, но не моделируют тактирование USART, работу DE/RE, реальные пины и электрику RS485. Сборку в IAR/ESP-IDF и прошивку на физических платах необходимо проверить отдельно. Порядок проверки на оборудовании: сначала одна головка (`SNAP` → `STATUS` → `READ`), затем две; при вращении контролировать `seq`, угол, сектор, счётчик `sample` и время. Убедиться осциллографом, что на вещание нет ответов и два slave не включают передатчики одновременно. Длительные секции DMA/EEPROM/калибровки могут мешать приёму 115200 бод: смотреть `cycles_max`, `serrcnt1`, `errorflag` и ошибки линии. В существующем ПО приоритеты прерываний: DMA2_Stream3=0, TIM4=1, USART1/TIM2=2.

## 7. Командный интерфейс калибровки (без SPI)

Старая карта FC04 **0..10 не меняется**, включая замороженное поле 6.
Для калибровки используется отдельный LIVE-диапазон, не требующий SNAP или
валидного кадра АЦП. Это позволяет видеть ход калибровки при `ready=0`.

| Тип | Адрес на линии | Значение |
|---|---|---|
| FC06 holding | 1 | Команда: `0x10` STOP, `0x11` проход 1, `0x12` проход 2, `0x13` offset, `0x14` buf_k |
| FC04 input | `0x100` | Текущий `encoder_state` (0x00..0x80), НЕ frozen |
| FC04 input | `0x101` | 1, когда `i2c3_tx_wp != 0`: передача EEPROM завершена, иначе 0 |
| FC04 input | `0x102` | `0xCA01`: сигнатура/версия этого командного интерфейса |

Поддержано чтение поддиапазонов внутри каждого блока, но не через промежуток
11..255. Командные записи только FC06, count=1. Чтения holding/FC16 не включены.
Неизвестная команда/неподготовленный проход 2 → exception 03; занятость автомата
или EEPROM → exception 06; неверный диапазон → exception 02.
**Broadcast разрешён только для SNAP**: калибровочная запись на ID 0 игнорируется
до прикладного callback, без выполнения и без ответа.

### Переключение автоматов STM32 по командам

Цепочка вызовов: `main()` → `eMBPoll()` → `eMBRegHoldingCB()` →
**`encoder_calibration_command()`** в `Src/encoder_calibration.c`.
Модуль включён в `EWARM/taos.ewp`; интерфейс — `Inc/encoder_calibration.h`.
Обработчик регистров только преобразует результат команды в код Modbus.
SPI, его DMA/IRQ, буферы и формат пакетов не возвращаются.

Источник переноса — **исполняемый C-код** `spi_recv_process()`,
`case 0x10..0x14`, строки 5599–5640 файла
[`Src/main.c` из коммита 4151ab14a18038c5da68aab7dd27da33447cbb08](https://github.com/shroomjak/hard_encoder/blob/4151ab14a18038c5da68aab7dd27da33447cbb08/Src/main.c#L5599-L5640),
а не документация по нему.

| Команда | Подготовка алгоритма | Состояние после команды → после алгоритма |
|---|---|---|
| `0x10` | Снять флаги калибровок, сбросить `cycles_max`; остановить также buf_k, фазы offset/anglek = 101, разрешить АРУ | любое → `0x00` |
| `0x11` | `start_calibrate=1`; `angtab_cal()` инициализирует первый проход | `0x10` → `0x20` |
| `0x12` | `start_calibrate=2`; `angtab_cal()` инициализирует второй проход, сохраняя результат первого | `0x30` → `0x40` |
| `0x13` | `start_offset_cal=1`, счётчик усреднений и фаза = 0, **весь `offset_minmax[]=1.0f`**, `offset_cur=offset_start` | `0x50` → `0x60` |
| `0x14` | `start_angk_cal=1`, счётчик усреднений и фаза = 0, `buf_x3[]=0`, запретить АРУ | `0x70` → `0x80` |

Для `0x13` сохраняется настроенное окно `offset_start/offset_end` (исходно 63..65),
как в историческом обработчике; оно не перезаписывается при каждой команде.
Инициализация `offset_minmax` нулями в прежнем мосте заменена на исходное `1.0f`.

Сохранены защитные отличия от старого SPI-кода: занятые автоматы/EEPROM не
перезапускаются, `0x12` допустима только после `0x20`, перед проходом ang_tab
сбрасывается защёлка `old_sector=-1`. STOP останавливает **все** автоматы, включая
`start_angk_cal` (старый SPI case `0x10` его не сбрасывал), и разрешает АРУ.
STOP не восстанавливает таблицы, не отменяет I2C и не подделывает EEPROM_READY.

**Команда не подменяет выполнение алгоритма.** Она немедленно выставляет
стартовое состояние и флаги. В следующих валидных кадрах суперцикл вызывает
`offset_cal()`, `angk_cal()`, `angtab_cal()`; сами функции выставляют состояния
завершения `0x20/40/60/80`. Их исполняемый код сверён с указанным коммитом и
не изменён. Без валидных кадров/вращения прогресса может не быть.
Переход к следующей калибровке выполняется только новой командой; например,
`0x20` само не запускает второй проход. LIVE FC04 читает текущий `encoder_state`,
а не замороженное поле снимка. Коды `0x40/60/80` могут появиться до окончания
I2C-передачи — мастер обязан дополнительно ждать EEPROM_READY.

ESP32 выполняет **14 → 13 → 11 → 12 → 14 → 13** с ожиданием соответственно
**80, 60, 20, 40, 80, 60** и EEPROM_READY. Перед каждым этапом, в том числе
перед следующей головкой, требуется `next`; перед `12` оператор меняет вращение.
После последнего этапа — адресная `10` и проверка состояния `00`.
Проверяются версия интерфейса, исходное состояние, busy/done-коды, тайм-аут
10 минут и ошибки связи. [Полный сценарий и ограничения](../esp32_master/README.md#калибровка).

python3 tests/calibration_state_test.py # FC06 → реальные алгоритмы main.c → LIVE
sh tests/host/run_workflow_test.sh     # поиск, CLI-список, этапы, отказы
